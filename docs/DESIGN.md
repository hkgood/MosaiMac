# 设计决策与实测数据

MosaiMac 的技术细节。README 只留概览，这里放完整内容。

## 为什么是 1-bit

1984 年的 Macintosh 用 68000 @ 7.836 MHz、**128 KB 总内存**，跑出了完整的窗口系统：可拖动窗口、区域裁剪、脏矩形重绘、滚动条、下拉菜单。核心就是 BitBlt 和 Region。

这套东西今天依然适合嵌入式图形，因为**1-bit 是唯一一种在「没有 GPU、没有 DMA 引擎、没有 alpha」的设备上，还能把整屏重绘压进 16 ms 的位深**。480×320 是 18,750 字节，不是 460 KB。

## 位图约定

- 1 bit/pixel，**MSB-first**，行首像素是 bit 7
- `rowBytes` 是**行距，包含行尾 slack**
- `QD_SCREEN_ROWBYTES`（60）是**有效载荷宽度**，位运算基于它
- 每行需要 `QD_ROW_SLACK`（8）字节可读余量，成本 8 B × 高度 = 2.5 KB

最容易错的是第二和第三条的区分。引擎靠 `rowBytes` 找下一行，所以它必须包含 slack；而位运算只关心载荷。**把 `rowBytes` 设成有效载荷宽度、却按行距分配内存，会静默地把图像剪切成斜的** —— 写的人和读的人对「第 N+1 行从哪开始」意见不一致。`QD_SCREEN_STRIDE` 就是为这件事命名的。

ROP 引擎把非对齐的源数据过 64 位窗口滑动，最多会多读 8 字节；部分字节的辅助函数多读 1 字节。两者都停在行距之内，所以 slack 是有界的、可计算的。

## 屏幕尺寸

**内部 480×320，不缩放 512×342。**

原版屏幕 512×342，这里是 480×480。`480/320 = 1.5`，`512/342 ≈ 1.497` —— 宽高比本来就是一致的。缩放会多一整个重采样阶段，而收益是零。

代价：行距 60 字节，让每行都 16 字节不对齐。ROP 内层循环会慢一点。值得付。

布局上 480×320 垂直居中在 480×480 面板里，上下各 80 px 黑边。

## Region 表示

原版把 Region 塞进 `Region` record 允许的 16 字节，运行长度编码，每个集合运算都是手写位运算。

S31 有 16 MB PSRAM，所以用内存换可验证性是白赚的：span list 更容易测，也更适合逐扫描线的 BitBlt。

- **矩形 Region 原地存储**，`offsets == NULL` 即 `qd_region_is_rect()`，零堆分配，ROP 直接跳过逐扫描线遍历
- **一般 Region** 是两个平面数组：`spans`（所有行的 span 首尾相接）+ `offsets`（前缀和表）
- 前缀和表是必要的：按行存 span 数量会让 `qd_region_spans()` 变成 O(y)，整屏 blit 因此是平方复杂度

内存占用：典型矩形 region 1.2 KB；病态的每行 60 span 棋盘格 37.5 KB（实际绘图不会产生这种形状）。

## 脏矩形：最重要的一条

窗口移动损伤的是新旧位置的对称差。**怎么存这个数，帧率差一个数量级。**

| 存储方式 | 1 像素拖动的损伤 | 推送量 | 40 MHz QSPI 上的帧率 |
|---|---|---|---|
| 矩形（包围盒） | 40,800 px | 82 KB | 46 fps |
| Region + 逐 run 切分 | **818 px** | **1.6 KB** | 交互无碍 |

**取包围盒永远是整个窗口** —— 因为对称差是个 L 形，它的包围盒就是窗口本身。哪怕只拖 1 像素。

`qd_bsp_flush()` 会把竖直方向相同的 run 合并成极大矩形，所以一次窗口移动的损伤塌缩成大约 4 个矩形，而不是每条边每行两个。

`test/test_window.c` 在没有硬件的情况下验证整条回路：拖动窗口，每一步之后断言窗口外**没有任何残留黑像素**（那就是漏掉的损伤，落到面板上就是拖影），断言标题栏和边框确实画出来了，断言被跨过的下层窗口完好。

## 实测

主机：x86-64、GCC 12、`-O2`。S31 会更慢 —— **有参考价值的是比例，不是绝对值。**

```
CopyBits 全屏 480×320
  srcXor   对齐        0.007 ms      22,000 Mpixel/s
  srcOr    对齐        0.007 ms
  srcCopy  对齐        0.006 ms
  srcXor   非对齐      0.047 ms       3,270 Mpixel/s
  srcXor   L 形 region  0.014 ms      10,600 Mpixel/s
  200×150 窗口移动     0.011 ms      90,600 ops/s

1bpp → RGB565
  整帧                 0.150 ms       1,030 Mpixel/s
  120×90 脏矩形        0.011 ms

面板开销（模型估算，不是实测）
  @ 40 MHz QSPI: 整帧 21.9 ms (46 fps) | 120×90 脏矩形 1.54 ms (648 fps)
  @ 80 MHz QSPI: 整帧 11.0 ms (91 fps) | 120×90 脏矩形 0.77 ms (1296 fps)
```

**瓶颈是 QSPI 链路，不是 ROP。** 一个完整 RGB565 帧是 300 KB（1bpp 帧缓冲只有 18.75 KB），链路估算 14–28 MB/s。所有关于更新粒度的决策都从这一个事实来。

CO5300 要求窗口偶数对齐，所以脏矩形必须**向外**取偶 —— 向内取偶会留下没被推送的列，也就是拖影。

## 两处被实测数据逼出来的优化

**非对齐 BitBlt 曾经比对齐慢 14 倍。** 走的是逐字节分块路径：每个目标字节都要重载 16 位源窗口、移位、再 switch 一次 mode。拖窗口天生非对齐，而且是 Mac 式 UI 里最频繁的 BitBlt，不能忍。改成把源数据过 64 位窗口滑动：0.104 → 0.047 ms，200×150 窗口移动 0.021 → 0.011 ms。

**`qd_region_spans()` 原本每次查询是 O(y)。** 换成前缀和 offset 表后：0.040 → 0.014 ms。

## 拖动动画暴露的两个坑

README 里那段 GIF 不是录屏，是 `tools/replay.c` 驱动真实拖动、逐帧导出的。做它的时候撞到两个静态图永远暴露不了的东西：

**drop shadow 伸在窗口矩形之外。** 阴影画在 `r.right+i` 和 `r.bottom` 之外，而 damage 是按窗口矩形算的。结果是每一步移动都留下一道阴影残影。真实的窗口管理器一定会踩这个 —— 阴影是 QuickDraw 窗口的标准外观。正确做法是 damage 用**视觉边界**（窗口 + 阴影），绘制才用窗口矩形。

**露出的地面不是空白。** 把 damage 区域填白，在下面什么都没有时是对的；一旦底下有桌面图标，那些图标就被擦掉了。QuickDraw 应用的做法是**自底向上重绘 damage 区域**：先重绘背景，再画窗口，region clip 保证只碰损伤的扫描线。

`tools/replay.c` 里两个都实现了。但桌面图标仍然没放进 GIF：窗口 bounce 的上限离屏幕底部还远，放在那里的图标只会被"露出"而不会被"遮挡"，而"露出"正是上面第二条较难的那一半。在重绘路径还没打磨完的时候把它放进 README 动画，等于发一张会骗人的截图。`tools/render.c` 里有图标，`test_window.c` 里也测了窗口跨窗口，那两条路径不是没测，只是不在这段 GIF 里。

## 引擎踩过的坑

每一个在常见路径上都看不见。现在每一条都有回归测试。

**`rop_byte_chunk()` 少了一次按目标位相位的移位。** 源 bit 打包在字节顶部，直接拿去和目标掩码相与，只在 `dp == 0` 时正确 —— 也就是**所有非对齐 span 全错**。整字节路径把它盖住了。

**`qd_fill_span_1bpp()` 的部分字节掩码忽略位相位。** 用 `0xFF << (8 - n)` 写的，只在 span 恰好结束在字节边界时正确。head/tail 一被裁剪就错 —— 第一次暴露是 `frameRect` 一个 3 px 边框被裁成 3 px。

**XOR 结果被截断到操作数 bounds 的交集。** 只有 INTERSECT 会被交集框住。XOR 和 UNION 都会伸出去，所以窗口移动的对称差（正是靠这个特性算的）会丢掉一整块。

**`spans_xor` 会丢 span。** 头尾合并和双游标都不对，因为一个 span 可能压住另一个列表的*下一个* span：`a = [0,10)+[30,50)` 对 `b = [5,35)`。必须对两组边界的并集做事件扫描。

**`qd_port_set_white()` 存在但 `qd_fill_rect()` 完全不理它。** 调用方设白笔期待擦除、实际得到黑色，而且**没有任何办法察觉**。现在按 QuickDraw 原意：`srcCopy` 用前景图案，`srcBic`/clear 用背景（即擦除）。

**空 Region 是个哨兵指针** `(int32_t*)1`，不是真的空区域。忘初始化会变成堆损坏 abort，而不是得到一个空 region。

**`region_binop()` 的 aliasing 路径对未初始化的栈变量调 `qd_region_copy()`**，而 copy 第一行就 dispose —— 野指针释放。之前的测试都碰巧 `{0}` 初始化了。

## 备选路线

**Linux on S31。** S31 没有 MIPI DSI，QSPI 屏要自己写 Linux SPI panel 驱动，而 Espressif 官方的 Linux BSP 面向的是无屏的 Function-CoreBoard。产物是 fbdev 控制台，不如真正的 1-bit 窗口系统有用。

**`systemless`。** 一个活跃的 Rust 经典 Macintosh 运行时，是找到的最接近的先例。GPL-3.0-or-later，Cranelift JIT 那条线目前主要是 x86-64，对 S31 不是直接路径。兼容层值得研究，图形引擎不值得抄。

**Apple 的 QuickDraw 源码。** 没有使用。**接口**是重新实现的，**没有一行代码是抄的**。

## PPA 为什么不用

PPA 主要加速 RGB 图层合成，而 QuickDraw 的 ROP 是 1-bit。把它塞进 PPA 会多一次格式转换，去避免 CPU 本来就做得很好的工作。

## 已知问题

1. `set-target esp32s31` 在你的 IDF 里可能还不存在（preview 芯片），需要指到 Espressif 的 preview 分支
2. ESP-IDF 平台层**从未编译过**
3. QSPI 时钟 40 MHz 是假设值，实测之前别信帧率估算
4. S31 的 ISA 字符串官方没公开公开说明，「无 RISC-V V 扩展」来自二手资料。引擎是纯 C，要用 SIMD 得重写
